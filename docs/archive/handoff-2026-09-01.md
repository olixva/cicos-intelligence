# Handoff — Allianz CICOS Claims Intelligence

## Purpose and delivery expectation

This repository implements a local, production-shaped RAG technical exercise around the supplied
`Manual-cide-ascide-y-cicos.pdf` (111 PDF pages; SHA-256
`b9c70c74911fad7992a01f77d861a33f10f8313c96a9f58c09b2f448a54c8344`). The requested product has
two explicit flows and one future automatic router:

1. **Document question**: answers only from the manual with auditable citations.
2. **Claim analysis**: extracts attributed facts from a user narrative, retrieves manual criteria,
   applies deterministic guards, and must not present a general liability opinion.
3. **Auto**: will select exactly one of the existing flows; it must not duplicate either flow.

The user wants backend and frontend separated by folders as if separate repositories, while still
in this Git repository. The backend must use lightweight hexagonal/clean architecture:
`domain`, `application/ports/inbound`, `application/ports/outbound`, and
`infrastructure/adapters/inbound|outbound`. FastAPI is infrastructure because it depends on the
framework. LangGraph is intentional: distinct question and claim graphs. Execution is entirely
local; Langfuse and Qdrant run locally with the `allianz-rag` Docker/Colima setup.

The interview task is fundamentally a grounded RAG over the supplied manual. Claim analysis and
the three modes are deliberately presented as an optional, clearly scoped enhancement, not as a
claim that the app offers general insurance advice.

## Safety and quality decisions

- Never invent CIDE matrix values, rules, legal currency, or table mappings.
- The 2004 manual is the source scope; do not state that it is current law.
- A user-provided claim is distinct from retrieved manual evidence.
- Facts retain `asserted_by` and literal `source_text`; contradictions stay explicit.
- A deterministic applicability gate prevents an inapplicable convention from resolving a claim.
- The verified manual rule currently implemented: CIDE/ASCIDE needs exactly two vehicles and a
  direct collision; an identified third vehicle or a chain collision makes the convention
  inapplicable. These points are supported by PDF pages 56–57, but the graph must only cite
  actually retrieved evidence IDs.
- The CIDE 18×18 matrix is **not** transcribed or usable yet. Docling’s page 101 table extraction
  has misplaced/mis-grouped cells; do not construct `data/rules/cide-matrix.json` until two
  independent visual transcriptions plus footnotes/orientation validation exist.
- Golden data is the source of truth for evaluation. It must be generated from curated evidence,
  blind-reviewed/adjudicated, partitioned by family, and frozen by manifest. Do not manufacture a
  “golden” dataset to make metrics look complete.
- Paid OpenAI calls are permitted, but use inexpensive models and do not spend materially without
  need. The existing key is in ignored `.env`; never read, print, commit, or reproduce it.

## Architecture already implemented

### Ingestion, source evidence and retrieval

- Baseline and Docling ingestion preserve physical pages, immutable source hash and page IDs.
- Structured extraction artifacts are under `data/extractions/<hash>/...`; active source includes
  `docling-2.124.0-pdfium-5.13.0-rapidocr-latin-torch-r2-3d1d1af9689b76cf`.
- The active collection alias is `allianz-manual-active`; a published index contains 109 chunks.
- Retrieval is interchangeable dense OpenAI embeddings + Spanish FastEmbed BM25 + native Qdrant
  RRF. Index signatures prevent incompatible reuse.
- Question LangGraph is at
  `backend/src/infrastructure/adapters/outbound/question_workflow/langgraph_workflow.py` and has
  `retrieve → generate → validate` nodes. It validates citations against the exact delivered
  context groups.

### Questions

- Domain/application models: `backend/src/application/models/query.py`.
- Inbound port: `application/ports/inbound/answer_question.py`.
- Bootstrap: `build_answer_question(profile_name)` resolves profile/publication/index and loads
  a numbered Langfuse prompt (`document-question`, version configured by environment). It creates
  a Langfuse trace ID and LangChain callback; generation uses Responses structured output with
  `store=False`.
- A real smoke question on traffic-light version disparity completed with grounded citations.
- Newly committed explicit API: `POST /api/v1/questions/answer`.
  It is mounted only when `create_app(answer_question=...)` gets the inbound port. It returns
  status, blocks, delivered context/source metadata and trace ID, intentionally omitting
  `image_path` and other local paths. Provider failures stay HTTP 500 rather than becoming
  `insufficient_evidence`.

### Claim analysis

- Domain models:
  - `backend/src/domain/models/claim.py`: `ClaimInput`, `ClaimFact`, `ClaimContradiction`,
    `ClaimEvidenceBlock`, `MatrixCell`.
  - `backend/src/domain/models/decision.py`: `ClaimAnalysis`, `MatrixLookup`, invariants.
- Applicability rule: `backend/src/domain/rules/applicability.py`.
- Deterministic CIDE matrix lookup guard: `backend/src/domain/rules/cide_matrix.py`; it resolves
  nothing without confirmed prerequisites and does not contain a real matrix artifact.
- Use case/ports: `application/ports/inbound/analyze_claim.py`,
  `application/ports/outbound/claim_workflow.py`,
  `application/use_cases/analyze_claim_use_case.py`.
- LangGraph claim workflow:
  `backend/src/infrastructure/adapters/outbound/claim_workflow/langgraph_workflow.py` has
  `extract_facts → retrieve_criteria → apply_rules → explain → validate`. The LLM extraction
  cannot overwrite the deterministic result.
- OpenAI fact extractor:
  `infrastructure/adapters/outbound/language_model/openai_claim_fact_extractor.py`, structured
  Responses output, only receives claim/clarifications, uses `store=False`.
- Bootstrap composition exists as `build_analyze_claim(profile_name)` and reuses active retrieval
  mechanics. It is ready to be injected into the API but no production API dependency wiring
  exists yet.

### Evaluation and observability

- Golden schema/release validation is implemented. Manifests validate schema version, SHA-256,
  partitions, IDs and counts.
- Evidence metrics implemented: AND/OR coverage, citation precision/recall and cost per success.
- `langfuse_experiments.py` includes `build_question_task` and `serialize_execution`; it selects
  only `input.text`/`input.language`, never expected reference/metadata. Serialized context has
  only actual delivery/source identity, not raw pages.
- Newly committed Ragas adapter:
  `infrastructure/adapters/outbound/evaluation/ragas_evaluators.py` uses installed public APIs
  Ragas 0.4.3 `FactualCorrectness.ascore(response, reference)` and Langfuse 4.15.1 `Evaluation`.
  It consumes only serialized `output["answer_text"]` and `expected_output["reference"]`.
- Langfuse prompt `document-question`, v1, was created locally. Do not rely on mutable aliases in
  production composition.
